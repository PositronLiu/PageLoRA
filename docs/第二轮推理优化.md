# 第二轮推理优化：实现与验证方法

当前状态：实现完成，19 项标准库回归测试通过；新增 tensor 测试、GPU 正确性和性能消融待运行。原 H800 SSH 端口连接被关闭，尚无本轮加速结果。上一轮 1.80× 是 Graph 相对 eager 的已有结论，不能当成本轮优化收益。

## 优化一：直接用 CPU 元数据规划 decode

原路径每个 token 在 CPU 根据 KV spans 构造页表，将 indptr、indices、last_page_len 写入 GPU，再调用 FlashInfer plan。核对 FlashInfer 0.6.6 后发现，plan 会把 indptr 与 last_page_len 读回 CPU，形成不必要的 CPU→GPU→CPU 往返，可能让主机等待先前的 GPU 工作。

新路径从 spans 直接构造独立的 pinned CPU 页表，交给原生 plan；plan 用 CPU 元数据做规划，并以 `non_blocking=True` 上传到原有持久 GPU 页表。没有跳过 plan，也没有假设页内长度变化时计划恒定。

安全措施：每次规划使用新的、之后不修改的 CPU 张量；CUDA event 记录上传完成点，在 event 完成前保留源张量。最多保留 8 组，队列满时等待最老 event，避免异步复制期间复用主机内存或无限增长。Graph 仍跟踪包装器、host 计划和缓存变化；GPU 页表显式在后端 GPU 上分配，不会因输入元数据位于 CPU 而误分配。

开关：`MINI_OPENCLAW_FLASHINFER_HOST_PLAN=1`，默认 0。目前只改造单请求 decode，batch 和 prefill 保持已有路径。不采用修改 FlashInfer 私有 planner 的方案。旧 API 若不接受 non_blocking，会走已有兼容分支，可能退回同步复制，收益必须实测。

## 优化二：融合残差加法与 RMSNorm

原 Graph 的 post-attention 部分分开执行残差相加、RMSNorm。新路径在静态 decode 层内调用 FlashInfer `fused_add_rmsnorm`，减少一个独立算子及中间张量读写；单请求及 batch 静态 decode 都接入相同 helper。

该 API 原地修改两个输入，调用点只使用 Graph 拥有且之后不再需要旧值的中间张量。仅在无梯度、FP16/BF16、形状和 dtype 相容、连续且非同址的普通 RMSNorm 上使用；Gemma 等特殊归一化保留原路径。不满足条件时执行原有加法与归一化，不吞掉已开始执行的 kernel 错误。

开关：`MINI_OPENCLAW_FLASHINFER_FUSED_ADD_RMSNORM=1`，默认 0。融合可能改变低精度舍入，必须重新通过 token、logits、缓存复用与 Graph replay 门禁，不能仅凭数学表达式相同就启用。

## 四组消融与运行入口

| 组别 | CPU 元数据规划 | 融合 add + RMSNorm |
|---|---|---|
| baseline | 关 | 关 |
| host_plan | 开 | 关 |
| fused_norm | 关 | 开 |
| combined | 开 | 开 |

服务器代码同步后，运行：

```bash
python -m pytest test/test_flashinfer_backend.py test/test_flashinfer_norm.py test/test_flashinfer_cuda_graph.py -q

nohup python -u -m scripts.run_decode_optimization_experiments \
  --model /root/bayes-pub/models/DeepSeek-R1-Distill-Qwen-7B \
  --dtype float16 --prompt-lengths 512 2048 --output-tokens 128 \
  --warmup-runs 2 --measure-runs 10 --max-model-len 8192 \
  --output-dir /root/bayes-tmp/pagelora-optimization \
  > /root/bayes-tmp/decode-optimization.log 2>&1 < /dev/null &
```

入口会清除继承环境中对这两个开关的干扰，为每组显式赋值；每组先过 HF/eager/Graph 正确性门禁，再测 core。baseline 额外跑 vLLM 正确性及 HF/vLLM 性能，避免每组重复初始化成熟框架。完整四组共 20 个性能任务、200 次正式请求，不包括预热与正确性请求。若某组门禁失败，立即停止，不产生该组性能结论。

脚本只在 GPU 子进程导入依赖，`--dry-run` 可在本地查看计划。原始结果位于 output-dir 下新建的 `decode_optimization_时间戳/`，精简证据自动归档到项目 `experiment_results/`；`comparison.md` 比较各组 Graph 与同轮 baseline Graph，保留负收益，不把原来的 eager→Graph 收益重复计算。源码快照、环境、日志、CSV 和运行状态一并保存，实验中修改源码则运行不算成功。

若预算有限，先用 `--variants baseline host_plan --prompt-lengths 512 --measure-runs 3` 预筛选；预筛选不能代替正式结论。新优化过门禁且有稳定收益后，再考虑调整默认配置、更新正式报告和 PPT。

## 开源参考与归因

- [FlashInfer 0.6.6 decode wrapper](https://github.com/flashinfer-ai/flashinfer/blob/v0.6.6/flashinfer/decode.py)：核对 plan 的 host 元数据读取、non_blocking 参数和持久页表行为。
- [FlashInfer 归一化 API](https://docs.flashinfer.ai/api/norm.html)：使用其公开 fused_add_rmsnorm 算子。

本轮通过依赖调用已有开源算子，新增代码为项目内调度、生命周期管理和消融流程，不将开源 kernel 表述为自研。FlashInfer 的许可及实现归原作者，具体复现版本随实验元数据保存。
