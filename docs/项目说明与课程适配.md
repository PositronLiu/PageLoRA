# PageLoRA 项目说明与课程适配分析

更新时间：2026-11-09。本文依据当前仓库代码与历史实验台账编写；本次没有在本地运行模型或 GPU 实验。

## 1. 这个项目是做什么的

PageLoRA 是一个面向单 GPU 的大语言模型推理原型，主要优化短交互、重复上下文和 LoRA 服务场景。它不是训练一个新模型，而是在已有 Transformer 模型上改进“模型怎样运行、历史注意力状态怎样存储、重复请求怎样少算一些”。

例如多个请求共享一段很长的系统提示词：普通推理每次都计算这段提示词的 KV；PageLoRA 可以检索已有前缀，将其 KV 页复用于后续请求，再计算各自不同的后缀。生成阶段则使用 FlashInfer 注意力内核与 CUDA Graph，减少逐 token 解码中的执行开销。

LoRA 是给基础模型增加低秩增量的方法。项目既能研究基础模型推理，也保留适配器切换、权重合并、低秩增量执行和显存协调等扩展。课程作业不必使用全部功能。

### 1.1 两个推理阶段

- **Prefill（预填充）**：处理输入提示词，计算 KV 缓存，并产生首 token 所需的 logits。长输入通常让这一阶段更昂贵。
- **Decode（解码）**：读取历史 KV，每轮生成下一个 token。batch 较小的时候，权重读取和大量小算子的启动开销很值得优化。

KV cache 存的是每层注意力的 Key/Value 张量，用显存换取避免重复计算。分页缓存将逻辑序列映射到固定大小的物理页；分页本身不保证速度提升，还需考虑页表维护、分配、注意力内核和缓存命中。

### 1.2 代码里的主要机制

| 机制 | 作用 | 主要代码 |
|---|---|---|
| 模型与配置管理 | 加载基础模型、选择运行路径、组织适配器 | `model/model_manager.py` |
| FlashInfer 注意力 | 使用 paged-KV attention 执行 prefill/decode | `model/flashinfer/attention_backend.py`、`generation.py` |
| 分页 KV | 分配页、维护请求页表、提交与中止请求 | `model/kvcache/paged_kvcache_manager.py`、`paged_kv_allocator.py`、`flashinfer_page_table.py` |
| Radix 前缀缓存 | 根据 token 序列寻找最长可复用前缀 | `model/kvcache/radix_cache.py`、`radix_storage.py` |
| CUDA Graph | 捕获并重放解码执行，避免每轮重新提交大量小算子 | `model/flashinfer/cuda_graph.py` |
| 投影与算子优化 | QKV/MLP 打包、归一化、编译路径 | `model/flashinfer/packed_ops.py`、`compiled_mlp.py`、`norm.py` |
| LoRA 运行时 | 合并/有效权重、A/B 低秩增量、适配器切换 | `multilora/`、`model/flashinfer/effective_weights.py` |
| 显存协调 | 在适配器权重和 KV 驻留之间协调压力 | `model/memory_aware.py` |
| 基准测试 | HF、FlashInfer、vLLM 与前缀复用实验 | `test/inference/` |

### 1.3 一次请求的大致路径

```text
输入文本 → chat template/tokenizer → token ids
        → 模型管理器选择 HF 或 FlashInfer 路径
        → 查询前缀缓存，申请剩余 KV 页
        → 计算未命中的 prefill
        → 逐 token decode（可启用 CUDA Graph）
        → 提交缓存、返回输出文本与计时
```

缓存正确性尤其重要：不同适配器或权重版本的 KV 不能随意互用；页被回收后也不能继续由旧请求引用。仓库已有 radix、分页缓存、页准入、图重放等测试，但服务器验证仍是本轮交付后的必要步骤。

## 2. 是否适合“单 GPU LLM 推理优化”

**适合，建议保留原工程并收紧研究范围，不需要重写一个新项目。** FlashInfer、分页 KV、前缀复用、CUDA Graph 都直接作用于单卡推理。需要适配的是实验问题、对照设计与成果表述。

建议课程题目：**《PageLoRA：基于分页 KV 缓存与 CUDA Graph 的单 GPU LLM 推理优化》**。

建议主问题：在同一张 GPU、同一模型与相同生成设置下，FlashInfer 路径及 CUDA Graph 如何影响端到端请求延迟？在共享前缀场景下，缓存复用可以节省多少请求时间？

### 2.1 必做与扩展

| 优先级 | 内容 | 原因 |
|---|---|---|
| 必做 | 基础模型 HF / FlashInfer / vLLM 对照 | 直接对应 LLM 推理，避免 LoRA 设置成为混杂因素 |
| 必做 | 同一 FlashInfer 配置 Graph off/on 消融 | 量化单项优化贡献 |
| 必做 | 前缀实验统一冷/热条件 | 避免把缓存状态差异误认为引擎优势 |
| 必做 | 固定生成长度、记录实际 prompt tokens、保存完整环境与日志 | 能复现，也能解释测量差异 |
| 必做 | 正确性和稳定性验证 | 提速必须建立在输出与缓存行为可信的基础上 |
| 建议 | 显存峰值、页数/命中 token 数、分阶段计时 | 解释为什么变快或变慢 |
| 扩展 | LoRA merge 与真正 A/B 增量路径对照 | 体现旧项目特色，但无需成为主线 |
| 暂缓 | 训练、在线强化学习、复杂多适配器调度 | 增加实现与解释成本，对本题主线帮助有限 |

分页 KV 的收益不能仅用 HF vs FlashInfer 的差异证明，因为这还改变了内核与执行路径。若要单独声称分页策略更优，应增加同后端的策略消融或显存/碎片证据。本轮脚本不声称已经完成该消融。

### 2.2 可验证的假设

1. 在小 batch 的 decode 中，Graph 重放可能降低 CPU 提交开销；不同模型与长度的收益不一定相同。
2. 共享前缀越长，复用 KV 越可能降低后续请求的 prefill 成本；总请求加速还取决于输出长度。
3. LoRA 合并可以减少解码的增量计算，但要考虑合并时间、额外权重显存以及切换成本，不能直接等同于多适配器服务优势。

这些是实验假设，并非本次新测结果。

## 3. 历史结果能怎么用

仓库 `docs/experiment_results_infer_engine.md` 记录了 RTX 3090 24GB 的历史实验，文档日期为 2026-05-29。该日期来自仓库；“去年做的项目”不等于所有实验都在去年完成。汇报时建议称“已有项目/历史实验”，不要推断实验年份。

其中 Qwen3-8B、约 2K 输入、128 输出的历史表记录：

| 配置 | 历史 decode tok/s |
|---|---:|
| LoRA merge，Graph off | 38.7156 |
| LoRA merge，Graph on | 46.6840 |
| LoRA A/B no-merge，Graph off | 29.8762 |
| LoRA A/B no-merge，Graph on | 45.2289 |
| vLLM LoRA | 45.1408 |

在上述表内，merge 的 Graph 收益约 20.6%，no-merge 约 51.4%。这只是历史配置下的记录，不能推断课程服务器也有相同比例，更不能声称全面超越 vLLM。

需要保留的限制：

- 历史原始日志主要指向被 git 忽略的 `.local` 目录，当前版本库中的汇总表不是完整复现证据。
- 历史 vLLM LoRA 部分使用零 LoRA，只说明服务路径开销，不证明非零适配器的输出质量或数值正确性。
- 旧前缀实验中 FlashInfer 每组清缓存，而 vLLM 在热缓存上测量；并且原 decode helper 会先做一个单 token 探测请求。历史两者首请求/复用请求的延迟不能作为同条件结果直接对比。
- 初始化时间受磁盘缓存、JIT/编译缓存和图捕获范围影响，不能直接据此宣称部署启动优势。
- 当前 decode tok/s 的旧口径与首 token 边界有关。主实验改以端到端延迟及 `生成 token 数 / 请求总时长` 为主，分阶段结果用作辅助，暂不混用不同后端的 decode 指标。

## 4. 本轮修改与检查边界

### 已完成的代码改动

1. 修复 README 中不能直接运行的示例：`--model-path` 改为实际支持的 `--model`，`--engine` 改为 `--prefix-backend`。
2. 修复 vLLM 前缀实验：采用单次请求的总耗时路径，避免 decode 单 token 探测提前预热缓存；复制参数后修改，避免污染调用方配置。
3. 统一两后端的 `--prefix-reset-cache-between-runs` 语义：为 true 时，每次 warmup 和 measure 序列开始前清理缓存；vLLM API 缺失或返回失败时明确报错，避免静默报告“冷缓存”。序列内后续请求仍允许复用。
4. 新增 `scripts/run_course_experiments.py`：串行运行单卡对照/前缀实验，记录命令、版本、GPU、环境变量和各任务日志；支持不加载模型的 `--dry-run`。
5. 添加针对缓存重置/前缀运行流程的回归测试，以及只依赖标准库的实验矩阵测试。

### 尚未验证的部分

本地缺少 torch/pytest，且按要求不运行本地模型。语法检查和实验脚本的纯标准库测试不等于 GPU 路径已验证。现有内核的模型兼容性、图重放数值正确性、显存上限、长序列稳定性和新增 vLLM 重置 API 适配，都需要课程服务器验证。没有证据的疑点不作推测性大改。

特别注意：FlashInfer 目前使用 perf trace 累计值提供分阶段计时。实验脚本保留 `MINI_OPENCLAW_FLASHINFER_PERF_LOG=1`，关闭强同步 `PERF_SYNC=0`；不能直接关 trace 后仍把其缺省的分阶段值当作真实测量。低层 CPU 计时也不能等同于 GPU kernel 执行时间。
