# PageLoRA 课程服务器实验指南

以下以 Linux + NVIDIA 单卡为例。本地不需要装模型或 CUDA；所有模型实验都在课程服务器执行。从仓库根目录运行命令。不要同时运行多个本项目 benchmark 争用同一张卡。

## 1. 先确认服务器条件

```bash
nvidia-smi
python --version
nvcc --version
```

记录 GPU 型号/显存、驱动、CUDA Toolkit、Python 与空闲显存。先确认课程允许使用的 GPU 和模型目录。模型建议先选一个 7B/8B 的稠密 decoder 模型；显存不足时换更小且现有后端支持的模型，先缩短上下文，不要立即引入量化这个新变量。历史记录主要使用 3090 24GB，不保证其它服务器可直接照搬。

## 2. 安装环境

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip check
python -c "import torch, transformers, flashinfer, vllm; print(torch.__version__, torch.version.cuda, transformers.__version__, flashinfer.__version__, vllm.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
```

`requirements.txt` 是原工程的固定版本组合，本轮未在服务器重新解析安装。若 pip 报 torch/vLLM/FlashInfer 依赖冲突，先保存报错；不要随意用 `--no-deps` 绕过。需要按照该服务器 CUDA 与 vLLM 支持矩阵统一版本，必要时分别建 PageLoRA/HF 和 vLLM 环境，并记录两边版本。FlashInfer JIT 可能还需要 nvcc、C++ 编译工具与 ninja；缺少时依据报错和服务器管理员建议补齐。

如果出现 conda `libstdc++`/ninja 问题，历史台账有 PATH/LD_LIBRARY_PATH 经验，但 venv 不一定适用，不要直接照抄其它人的绝对路径。

## 3. 正确性检查（服务器运行）

```bash
python -m unittest test.test_course_experiments -v
CUDA_VISIBLE_DEVICES=0 python -m pytest test -q
```

测试中可能因缺少可选后端/CUDA 条件而跳过，需保存通过/失败/跳过数量和原因。不要把“全部跳过”解释成 GPU 后端通过。发生失败时先发回完整报错与版本信息。

正式测速前还需做真实模型正确性验证：相同模型、token ids、dtype、无 LoRA、greedy 条件下，对比 HF 与 FlashInfer 的首步 logits 和生成序列；对比 FlashInfer Graph off/on、前缀清缓存/复用的结果；测试长输出跨页、部分页前缀、显存不足失败后的回收。如果输出分叉，保存首处分叉 token、logits 误差与前缀命中信息，再判断是数值边界还是实现错误。当前启动器只负责测速，不自动完成这项模型级正确性验收。

## 4. 最小冒烟实验

先把 `/path/to/model` 替换为服务器实际模型目录，`--gpu 0` 替换为分配的物理 GPU。启动器只向子进程暴露这一张卡，进程内使用 `cuda:0`；vLLM tensor parallel 固定 1。

```bash
python -m scripts.run_course_experiments --model /path/to/model --gpu 0 --prompt-lengths 512 --output-tokens 32 --warmup-runs 1 --measure-runs 1 --dry-run
python -m scripts.run_course_experiments --model /path/to/model --gpu 0 --prompt-lengths 512 --output-tokens 32 --warmup-runs 1 --measure-runs 1
```

会依次运行 HF、vLLM、FlashInfer Graph off、FlashInfer Graph on。任何任务失败即停止并保留日志，先修复再增加实验规模。路径含空格时给 `--model` 的值加引号。

当前矩阵统一使用 BF16：vLLM 显式设置，HF/FlashInfer 在支持 BF16 的 GPU 上自动选择该精度。启动前会检查 CUDA 与 BF16 支持，失败时保留 metadata 并停止。若服务器 GPU 不支持 BF16，需要为全部后端统一实现 FP16 配置后再比较，不要只改 vLLM 的 dtype。

## 5. 必做主实验与 Graph 消融

```bash
python -m scripts.run_course_experiments --model /path/to/model --gpu 0 --suite core --prompt-lengths 512 2048 4096 --output-tokens 128 --warmup-runs 2 --measure-runs 5
```

共 12 个任务，均为基础模型 `adapter-role=base`、相同 seed、greedy、禁用 logprobs、忽略 EOS 以固定输出长度。vLLM 默认 CUDA Graph/编译路径保留，FlashInfer 做显式 Graph off/on 消融。它们是“引擎整体对照”和“FlashInfer 内部消融”两个不同结论。

实际输入长度包含 chat template 和合成文本块，通常高于目标值；以日志里的实际 prompt token 数为准。启动器给 vLLM 的 `max-model-len` 默认 8192，扫描更长长度要同步调高且确认显存足够。

先跑 2K 再跑长度扫描也可以：`--prompt-lengths 2048`。完成后可把 `--output-tokens` 改为 512 做长 decode；每一组比较都保持相同输出长度。

## 6. 前缀复用实验

```bash
python -m scripts.run_course_experiments --model /path/to/model --gpu 0 --suite prefix --prompt-lengths 512 2048 4096 --output-tokens 128 --warmup-runs 2 --measure-runs 5
```

每种长度有 FlashInfer/vLLM × reset true/false 四项。每组 4 个串行请求，使用共享前缀与不同后缀。

- `reset=true`：每个 warmup/measure 序列开始前清缓存，第 1 个请求是 KV 冷请求，第 2–4 个请求允许复用。这里“冷”指前缀 KV，不指权重、文件系统或 JIT 冷启动。
- `reset=false`：保留 warmup 与测量之间的缓存，测量热缓存稳态。需要 warmup ≥ 1 才能解释为所有分支都预热后的结果。
- 比较两后端时必须匹配 reset 设置，不要拿一方的热请求对另一方的冷请求。
- 第 1 个请求与第 2–4 个请求的差异也含不同 suffix、分支位置和残余初始化影响。若需严格“缓存开/关的因果加速”，还要增加相同 prompt、同一引擎、每请求清缓存的对照。本轮启动器的序列冷/热比较不替代这项消融。

可单独复现某一项：

```bash
CUDA_VISIBLE_DEVICES=0 python -m test.inference.bench_prefix_caching --model /path/to/model --device cuda:0 --adapter-role base --prefix-backend vllm --prefix-bench-mode branch --shared-prefix-tokens 2048 --branch-suffix-tokens 64 --prefix-requests 4 --prefix-reset-cache-between-runs true --max-new-tokens 128 --ignore-eos --sampling-mode greedy_fast --compute-logprobs false --repetition-penalty 1.0 --throughput-timing total --warmup-runs 2 --measure-runs 5 --vllm-max-model-len 8192 --vllm-gpu-memory-utilization 0.8 --vllm-dtype bfloat16
```

若 `LLM.reset_prefix_cache()` 不存在或失败，脚本会报错，不会悄悄继续。保存版本/API 错误后再适配；显式改为 false 只能得到热缓存实验，不能称为修复冷缓存实验。

## 7. 指标与记录表

主指标采用端到端总时长和有效输出吞吐：`实际输出 token 数 / 请求总时长`。这样避免不同引擎 prefill/decode 计时边界造成误解。旧表的 decode tok/s 不要与这里的端到端 tok/s 直接混画。

```text
GPU / 模型 / dtype / commit / 环境
后端 / Graph 设置 / 缓存策略
实际输入 tokens / 实际输出 tokens
mean、p50、p95 请求延迟 / 端到端 tok/s
prefill、decode（辅助指标，注明口径）
前缀首请求延迟 / 复用请求延迟
GPU 显存观察值 / 错误与跳过原因
```

同一长度、同一配置至少 5 次测量；报告 p95 时说明样本较少，正式报告建议增至 20 次并重复独立进程。Graph 加速比按相同 FlashInfer 设置的 `off 平均总时长 / on 平均总时长` 计算，不用不匹配配置相除。

启动器不会自动报告精确的 PyTorch 显存峰值，也不把设备总显存与 KV 实占混为一谈。可在服务器另一个终端采样：

```bash
nvidia-smi --query-gpu=timestamp,index,memory.used,memory.total,utilization.gpu --format=csv -lms 200 > gpu_memory.csv
```

实验结束后 Ctrl+C 停止。该值包含同卡其它进程、引擎预分配且可能漏掉瞬时峰值，只能称“设备显存采样观察值”。若需严谨峰值，在各后端进程内加 `reset_peak_memory_stats/max_memory_allocated/max_memory_reserved`，仍要注明 vLLM 和外部内核分配可能不完全被 PyTorch 捕获。

## 8. 结果目录与发回材料

每轮写入 `course_results/<suite>_<UTC时间>/`：

- `metadata.json`：GPU、Python、pip freeze、commit、diff 摘要和相关环境变量。
- 每个任务的 `.log`：原始输出与报错，包含逐次测量和汇总。
- `runs.json`：已执行命令、日志路径与退出码。

复现实验前应提交或另外保存未提交 diff 与新增文件；当前 metadata 的 diff 摘要并非源码快照。不要提交模型权重到 git。

先发回最小冒烟实验目录、`pip check` 结果与 pytest 汇总；通过后再跑正式矩阵。拿到结果后可将 PPT 中“待验证”更新为本课程服务器的实际数值，并补上正确性和显存结论。
