# PageLoRA 单 GPU 大语言模型推理优化实验报告（初稿）

日期：2026-11-10。正式实验编号：`final_20261110T072511_252019Z`。

## 摘要

本项目围绕单 GPU 自回归推理，实现基于 FlashInfer 的分页 KV Cache、前缀缓存复用和 CUDA Graph decode，并与 Hugging Face（HF）及 vLLM 比较。在单张 NVIDIA H800 上，使用 DeepSeek-R1-Distill-Qwen-7B、FP16、固定输出 128 token 完成两档输入长度的实验。四条执行路径通过预设正确性检查，16 组性能任务、400 次正式请求测量全部有效。

在实际输入 529 和 2093 token 时，PageLoRA 的 Graph 路径相对自身 eager 路径分别加速 1.802 和 1.804 倍，达到 127.61 和 123.24 输出 token/s；vLLM 分别达到 168.87 和 162.95 token/s，仍快于当前实现。前缀复用对请求总耗时的改善较小，且短输入下存在负收益。本轮结果支持 CUDA Graph 在当前串行 decode 工作负载下的优化价值，尚不足以证明前缀复用的稳定收益或多 LoRA 服务能力。

## 1. 项目目标与技术路线

自回归生成每次只产生一个新 token。若逐步执行 Python 调度、页表准备和多个 GPU kernel，主机调度及 kernel launch 开销可能在重复 decode 中累积。项目将推理拆分为 prefill 与 decode：prefill 处理输入并写入分页 KV Cache；decode 根据页表读取历史 K/V，逐 token 更新缓存并生成输出。

主要实现包括：

1. **分页 KV Cache**：以页组织各层 K/V，用页表向 FlashInfer attention 提供历史上下文。
2. **前缀复用**：匹配已有前缀，复用相应缓存，减少重复 prefill。
3. **CUDA Graph decode**：捕获重复计算并 replay，降低逐 token 的主机调度开销。
4. **统一验证与计量**：在相同模型、精度、输入和输出长度下，对比 HF、PageLoRA eager、PageLoRA Graph、vLLM，保存逐请求 CSV、环境及正确性证据。

项目还包含 LoRA 管理相关代码，但本轮正式实验使用 **base 权重**，没有加载任务适配器。LoRA 是参数高效适配方法；本报告研究的分页缓存与 Graph 属于推理执行优化。两者可以组合，本轮数据不用于评价 LoRA 训练效果或多适配器并发性能。

## 2. 实验环境与设计

| 项目 | 配置 |
|---|---|
| GPU | 单张 NVIDIA H800，约 79.18 GiB 可见显存 |
| 模型 | DeepSeek-R1-Distill-Qwen-7B，公共盘本地权重 |
| 数值精度 | FP16，全部正式对照统一 |
| PyTorch / CUDA runtime | 2.10.0+cu128 / 12.8 |
| Transformers / FlashInfer / vLLM | 4.57.6 / 0.6.6 / 0.19.0 |
| 最大上下文配置 | 8192 token |
| 生成配置 | 固定输出 128 token，忽略 EOS，贪心生成，seed=42 |
| 预热与测量 | warmup=2，measure=10 |
| 主机线程 | OMP_NUM_THREADS=4，MKL_NUM_THREADS=4 |
| 负载 | 单 GPU、串行请求；不测并发服务吞吐 |

core 套件为 4 条执行路径 × 2 档输入，每组 10 次正式测量，共 80 次。prefix 套件为 2 个后端 × 2 档输入 × 2 种缓存策略，每组 10 轮、每轮 4 次请求，共 320 次。正确性用例单独执行，不计入这 400 次性能请求。

输入长度参数是构造目标，不能直接当成实际 token 数：core 的目标 512/2048 对应实际 **529/2093**；prefix 对应实际 **593/2179**。因此只在各套件内进行对应配置的比较，不把 core 和 prefix 的差异直接归因于缓存策略。

### 2.1 指标与比较口径

- **请求总耗时**：基准程序记录的生成调用总耗时，包含 prefill 与 decode，不包含模型加载；这不是 HTTP 服务延迟，也不是单独 decode kernel 的耗时。
- **输出吞吐率**：所有有效请求的输出 token 总数除以请求总耗时之和。它描述当前串行工作负载，不代表高并发服务的最大吞吐率。
- **Graph 加速比**：同输入、同输出和同后端配置下，eager 平均总耗时除以 Graph 平均总耗时。
- **p95**：样本耗时的经验分位数。core 每组只有 10 个样本，不能视作生产环境尾延迟保证。
- **显存**：加载、预热和测量全过程的整卡采样值，非精确进程峰值；vLLM 采用 0.8 显存利用率预算，不能据此直接比较内存效率。

## 3. 正确性验证及问题修复

性能测量前先运行正确性门禁，以 HF 为参考，测试 31、32、33、129 token 输入，每次输出 32 token，覆盖部分页边界及重复前缀场景。

| 检查内容 | 结果 |
|---|---|
| FlashInfer eager 与 HF 完整生成 token 序列 | 四组全部一致 |
| FlashInfer Graph 与 HF 完整生成 token 序列 | 四组全部一致 |
| vLLM 与 HF 完整生成 token 序列 | 四组全部一致 |
| FlashInfer 冷缓存与复用缓存输出 | 四组全部一致 |
| eager 与 Graph 输出 | 四组全部一致 |
| 首步全词表 logits（eager/Graph 对 HF） | 全部通过 atol=0.1、rtol=0.01 |
| Graph 实际执行证据 | 每个用例 62 次成功 replay |

首步 logits 最大绝对误差为 0.02734～0.07520，RMSE 为 0.00543～0.01265。vLLM 仅比较 token 序列，没有进行全词表 logits 对照；后续 decode 步也没有逐步进行 teacher-forced logits 检验。正确性报告的 `strict_pass=true` 表示通过这些预设用例，不能推广为任意输入均一致。

正式运行前解决了三个主要问题：

1. **GQA 比例兼容性**：模型 28 个 Q 头与 4 个 KV 头形成比例 7，原 FlashInfer CUDA-core decode 不支持；对不受支持比例选择 tensor-core decode。
2. **Graph 缓冲区生命周期**：普通 plan 可能替换 Graph 引用的内部缓冲区，导致后续请求非法访问；改用持久页表缓冲区，并将包装器与计划变化纳入 Graph 缓存失效条件。
3. **有限 mask 哨兵数值问题**：当前 FlashInfer 版本的有限负值 mask 与模型极端 QK 值发生冲突。将 Q 除以 16，并将 attention scale 乘以 16，在理论上保持有效 attention 分数，避免已观察输入触发该问题。该处理不保证任意极端输入范围。

BF16 在修复后虽有相同生成 token，部分首步 logits 仍超出默认容差，因此本轮统一使用通过原门禁的 FP16，没有放宽阈值。详细诊断见 [H800 正确性排障记录](H800正确性排障记录.md)。本轮修复另通过本地 15 项与服务器 16 项相关回归测试。

## 4. 核心性能结果

下表全部为输出 128 token 的测量；每行 10 个正式样本。

| 实际输入 token | 执行路径 | 平均总耗时 / s | p95 / s | 输出 token/s |
|---:|---|---:|---:|---:|
| 529 | HF | 1.9715 | 1.9737 | 64.93 |
| 529 | PageLoRA eager | 1.8072 | 1.8106 | 70.83 |
| 529 | PageLoRA Graph | 1.0030 | 1.0658 | 127.61 |
| 529 | vLLM | 0.7580 | 0.7599 | 168.87 |
| 2093 | HF | 1.8769 | 1.8790 | 68.20 |
| 2093 | PageLoRA eager | 1.8737 | 1.9480 | 68.32 |
| 2093 | PageLoRA Graph | 1.0386 | 1.0970 | 123.24 |
| 2093 | vLLM | 0.7855 | 0.7871 | 162.95 |

Graph 相对 eager 的加速比分别为 **1.802×、1.804×**，平均请求耗时均减少约 44.5%。相对 HF，Graph 分别为 **1.966×、1.807×**。这一消融说明，当前实现的主要可见收益来自 Graph，而 eager 单独相对 HF 的收益有限。

vLLM 的吞吐率分别约为 PageLoRA Graph 的 **1.323×、1.322×**。项目实现有效，但还未达到成熟框架在该负载下的性能。仅凭总耗时无法把差距分解到 attention、调度或融合算子，进一步归因需要 profiler 证据。

HF 在更长输入下反而略快，说明跨长度结果也受执行路径、GPU 状态及单次运行条件影响。不能从这两个点推导一般的长度增长规律。Graph 两档 p95 高于对应中位数，后续若强调稳定性，应增加独立重复运行。

## 5. 前缀复用结果

每组 40 次正式请求，均输出 128 token。reset=true 表示重置缓存的对照策略，reset=false 表示保留缓存的复用策略；下表速度比为重置组平均耗时 / 复用组平均耗时，小于 1 表示负收益。

| 实际输入 token | 后端 | 重置平均耗时 / s | 复用平均耗时 / s | 复用速度比 |
|---:|---|---:|---:|---:|
| 593 | PageLoRA Graph | 0.98287 | 0.99682 | 0.986× |
| 2179 | PageLoRA Graph | 0.99544 | 0.98033 | 1.015× |
| 593 | vLLM | 0.74872 | 0.74088 | 1.011× |
| 2179 | vLLM | 0.76308 | 0.75240 | 1.014× |

当前 workload 的总耗时收益约为 -1.4%～1.5%。PageLoRA 短输入下复用略慢，长输入下略快，不能表述为稳定加速。可能原因包括固定 128-token decode 占比较高、匹配及缓存维护开销，以及运行波动；本轮未完成阶段级剖析，这些只是解释假设。

各组还保存首请求与后续请求均值，可用于后续分析。但现有数据没有多个独立实验批次的置信区间，也没有证明上述小差异具有统计显著性。前缀复用在边界用例中已验证实际命中并保持输出一致，其性能价值仍应通过更长共享前缀、更短输出及重复批次检验。

## 6. 显存观察与 T4 预实验

core 中，HF 整卡采样峰值约 15.3～16.1 GiB，PageLoRA eager 约 23.6～24.1 GiB，Graph 约 24.6～25.0 GiB，vLLM 约 65.2 GiB。这些数值包含不同缓存预算及预分配策略，尤其 vLLM 使用 0.8 显存利用率预算，**不能据此声称 PageLoRA 的显存效率优于 vLLM**。

此前在 Tesla T4 上完成 1.5B 模型、FP16、HF 路径的预实验：实际输入 529 token、输出 32 token、3 次正式测量，平均耗时约 1.029 s、31.09 token/s，整卡采样峰值约 3923 MiB。该实验用于验证低显存环境下的运行与采集流程。因 GPU、模型和输出长度均不同，不与 H800 数值组成加速比。

## 7. 结论、局限与下一步

本轮完成了从模型加载、正确性门禁、性能消融到结果归档的完整流程。针对当前 7B 模型、FP16、单 GPU 串行负载，CUDA Graph 将 PageLoRA 相对 eager 的总耗时加速到约 1.80 倍；与 HF 相比约 1.81～1.97 倍。vLLM 仍领先约 32% 的输出吞吐率。前缀复用目前只有较小且不稳定的请求总耗时变化。

结论受以下范围限制：只验证一个正式模型、一张 H800、两档输入和一种输出长度；正确性用例较少；没有并发请求、LoRA 适配器或 OOM 恢复实验；没有独立重复批次和统计置信区间；没有经过 profiler 归因；BF16 仍存在待解释的 logits 误差。当前报告没有任务质量评测，生成 token 一致也不代表模型回答质量得到改善。

后续优先完成已有结果的图表与汇报整理。若继续追加实验，应按需要选择：多次独立运行核验稳定性；长前缀与短输出场景测量 TTFT/prefill；剖析 Graph 后的剩余瓶颈。多 LoRA 并发、量化及更多模型属于额外扩展，不能作为本轮已完成能力。
