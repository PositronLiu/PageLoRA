# H800 正确性排障记录（2026-11-10）

环境：H800、torch 2.10.0+cu128、FlashInfer 0.6.6、vLLM 0.19.0，模型为公共盘 DeepSeek-R1-Distill-Qwen-7B。以下是诊断记录，不是性能结论。

## 已修复：GQA group_size=7

模型有 28 个 Q 头和 4 个 KV 头，比例为 7。默认 CUDA-core decode 路径在 plan 时抛出 `Unsupported group_size: 7`。后端对这类比例选择 tensor-core decode；保留通常比例的原有选择。

## 已修复：Graph 引用已替换的计划缓冲区

原包装器以普通模式创建，但在外部被 CUDA Graph 捕获。tensor-core decode 的普通 plan 会重新分配内部 `qo_indptr`，旧 Graph 仍可能引用旧地址。冷热请求交替到 33-token 用例时触发非法显存访问，报错可能延后到下次页表写入。

现在 decode 包装器使用 `use_cuda_graph=True` 和持久页表缓冲区；批大小或索引容量变化时重建包装器。tensor-core 路径显式选择 FA2。Graph 的缓存键同时跟踪包装器及 host 计划，避免复用不匹配的捕获。eager/graph 共用此安全后端策略，消融不额外改变内核选择。

H800 定向验证：31/32/33/129 token 四组冷热请求均完成，每组 62 次成功 replay；冷请求的 graph/eager token 序列四组均相同。后端与 Graph CPU 回归测试 15 项通过。该验证不覆盖任意长度、并发或 OOM 恢复。

## 已修复：有限 mask 哨兵与大幅值 QK 分数

逐层相同输入对照将大误差定位到最后一层 attention。K/V 缓存与参考张量完全一致，但部分头在只有一个可见 token 时没有返回对应 V。FlashInfer 0.6.6 的 `math.cuh` 将 `math::inf` 定义为 `5e4`，其 mask 使用有限负值；本例存在更负的原始 QK 点积，使被屏蔽位置可能胜出。

后端将 Q 除以二的幂 16，并将 `sm_scale` 同比例乘以 16，保持理论 attention 分数不变，远离当前模型触发的有限哨兵区间。prefill/decode 同时处理，兼容 API 分支不允许丢失补偿 scale。该方案针对已观察数值范围验证，并非对任意极端输入的无穷 mask 保证。

独立 FP32 attention 对照中，最后一层 attention RMSE 从约 1.31 降到约 0.003；使用相同逐层输入和参考 RoPE 的 logits RMSE 从约 0.48 降到约 0.01。最终默认优化路径下，四组完整 token 输出均与 HF 一致，冷热输出一致，eager/graph 输出一致，每组成功 replay 62 次。后端与 Graph 回归测试新增有限 mask 场景，共 16 项通过。

## 尚未通过：BF16 全词表 logits 阈值

修复后的 BF16 数值检查仍未严格通过：完整输出 token 均相同，但首步全词表 logits RMSE 约 0.047～0.105、最大误差约 0.219～0.563，部分位置超出默认 atol=0.1、rtol=0.01。因此仍保留失败状态，没有放宽阈值。原有 vLLM/HF 的 33-token 用例分歧也需要独立处理。

原始报告：`final_20261110T063758_824824Z/correctness_20261110T063806_127597Z/report.json`，已下载到本地 `raw_results/`。

- 31/32 token 用例在第 26/25 个输出位置出现分歧（从 0 开始计）。

保持严格门禁，不将上述情况标记为通过，不生成性能加速结论。后续应以相同输入的逐层输出及 teacher-forced logits 定位差异，并记录分歧处 top-2 margin；不能只增大容差或删除失败用例。

## 修复后 FP16 定向验证

`correctness_20261110T071304_371938Z` 的 HF、FlashInfer eager、FlashInfer graph 三后端严格检查通过，沿用原 31/32/33/129 用例与默认误差阈值，没有删除用例或调整容差。报告覆盖完整 token 序列、首步全词表 logits、冷热输出与实际 graph replay。

随后单独执行 vLLM FP16 worker，同一 cases.json 的四组完整 token 序列均与上述 HF 结果一致。证据为 `pagelora-debug/vllm_fp16.json` 与 `vllm_fp16_fixed.log`。这是组合定向验证，正式流水线仍应重新跑四后端总门禁，不应将三后端报告篡改成四后端通过。

正式实验可以选择统一 FP16，以此验证结果为依据；BF16 仍作为未通过当前 logits 阈值的独立结果保存。不能将 BF16 基线和 FP16 优化结果混合计算加速比。

## 实例环境问题

FP16 首次 vLLM 编译时，Triton 未从动态链接器缓存找到实际存在的 `libcuda.so.1`。设置 `TRITON_LIBCUDA_PATH=/usr/lib/x86_64-linux-gnu` 后编译与输出对照成功。单卡 worker 使用本机回环地址，避免依赖平台损坏的主机名解析；没有修改宿主机网络或驱动。

两套实验 CLI 现在会在驱动库路径存在时补充该 Triton 环境变量，并为单卡本地 worker 设置默认本机地址。用户已有显式环境设置优先，实际环境写入 metadata。
